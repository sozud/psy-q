圧縮画像データ(BSフォーマット)

ここでは、MDEC および libpress で使用している画像データの形式と、そのデータの作成方法について解説します。

↑1 原画像データ

MDEC での原動画像データは、16m x 16n (m,n: 自然数) ピクセルからなる RGB24bit (R:G:B=8:8:8bit) の画像が時間軸に沿って複数枚ならべられているものが想定されます。この画像各１枚をフレームと呼びます。MDEC ではフレーム間の相関を利用した処理を行なっていないため、各フレームは独立に処理することができます。

MDEC では、フレームを 16x16 ピクセルの小領域の集まりとして扱います。この小領域をマクロブロックと呼びます。MDEC はデコード結果をマクロブロックの形でメインメモリに書き戻します。これを再構成して一枚のフレームを構成するのは CPU および GPU の処理になります。

例えば、320x240 の画像データは、以下のように、16x16 の多数のマクロブロックに分解され、それぞれがマクロブロック単位で圧縮されます。


このためフレームのサイズは縦・横ともに 16 の倍数になることが望ましく、これ以外のサイズの場合は工夫が必要になります。

↑2 マクロブロック分解

フレームの各ピクセルは通常左上から右下にかけて順番に並べられています。エンコードにあたってはこれをマクロブロックごとにまとまるようにピクセルの順番を並べかえます。
        
        #define WIDTH	320
        #define HEIGHT	160
        
        typedef struct {
        	u_char	r, g, b, pad;
        } PIXEL	
        
        make_macro_block(frame, macroblock)
        PIXEL frame[HEIGHT][WIDTH];
        PIXEL macroblck[][16][16];
        {
        	int ox, oy, x, y, i = 0;
        
        	for (ox = 0; ox < WIDTH; ox += 16) {
        	    for (oy = 0; oy < HEIGHT; oy += 16, i++) 
        		for (y = 0; y < 16; y++)
        		    for (x = 0; x < 16; x++)
        			macroblock[i][y][x] = frame[oy+y][ox+x];
        		}
        }
このときマクロブロックは左上から縦方向に並べられます。こうすることによって必要となるフレームバッファへの転送命令(LoadImage)の回数を軽減することができます。以下にフレームバッファへの転送の例を示します。
  • マクロブロックを左から右に並べる場合： 
        
        	for (y = 0; y < HEIGHT; y += 16)
        		for (x = 0; y < WIDTH; x += 16) {
        			setRECT(&rect, x, y, 16, 16);
        			LoadImage(&rect, p);
        			p += 16*16;
        	}
  • マクロブロックを上から下に並べる場合： 
        
        	for (y = 0; y < HEIGHT; y += 16) {
        		setRECT(&rect, x, 0, 16, HEIGHT);
        		LoadImage(&rect, p);
        		p += 16*HEIGHT;
        	}

↑3 RGB-YCbCr 変換

MDEC では途中の処理を YCbCr 色表示系で行ないます。そこで、RGB 色表示系で表現されたマクロブロック (RGB マクロブロック) は、YCbCr色表示系へ変換する必要があります。これを CSC (Color SpaceConversion) と呼びます。
ピクセルの各輝度値は、(R,G,B) を成分とする３次元空間上の点として表現できます。CSC はこの座標系（色空間）の座標変換と考えられます。

MDEC ではピクセルの輝度値は処理の最後に RGB 色表示系に変換されます。その際には、以下の変換式を使用します。

        R = 1.0*Y + 0     *Cb +1.402 *Cr;
        G = 1.0*Y - 0.3437*Cb -0.7143*Cr;
        B = 1.0*Y + 1.772 *Cb +0     *Cr ;

従って RGB 表示系から YCbCr 表示系に変換するにはこの変換に用いた行列の逆行列を使用します。movconv エンコーダはこの係数を使用しています。

        Y  =  0.299  *R + 0.587  *G + 0.114 *B
        Cb = -0.16871*R	- 0.33130*G - 0.5   *B
        Cr =  0.5    *R - 0.4187 *G - 0.0813*B

物理的には Y 信号は輝度信号、Cb,Cr は色差信号を意味します。白黒のＴＶセットは Y 信号のみを使用します。逆に白黒の画像であれば、Cb,Cr 成分はすべて０になります。

フレームバッファに RGB 表示系で記録された輝度値は、PlayStation内でYCbCr 系に変換されビデオ信号としてビデオ端子（Ｓ端子）から出力されます。受像器（ＴＶモニタ）はこのビデオ信号を受けて再びRGB 系に変換し、RGB の各成分に対応した電圧を電子ビームに与え、これがブラウン管上に並べられた蛍光体を発光させます。これが最終的な画像としてユーザに認識されます。

ここに至るまでの何回かの色空間の変換によって、最終的な出力の色合いが期待している色合いと異なる場合があります。これにはγ補正の係数のずれによるものと、変換行列のずれによるものが考えられます。

一般に電子ビームの電圧と輝度値は正比例しません。そこであらかじめ、輝度値には電子ビームの特性を考慮した補正がかけられています。
これをγ補正と呼びます。

一般に、受像器の蛍光体の発光輝度Ｂと入力電圧Ｅは以下のようなべき乗の関係にあります。

        B = pow(aE, γ);

そのため、送信側ではあらかじめ RGB の信号を1/γ乗してあります。しかし、この γの値は、受像器によって微妙に異なります。

特にコンピュータグラフィックス（ＣＧ）で作成された画像は、γ補正がコンピュータの高精細モニタにあわせてあったり、あるいはハードディスクにファイルとして記録された状態では何の補正も施されていない場合があります。γ補正が正しくなかったり、されていない場合は、エンコードのここの段階で正しく補正しておく必要があります。
ＣＧの画像を最終的に表示した時に期待していたよりも輝度値が暗い（明るい）場合はこれが原因の可能性があります。
一方、受像器の発光体の特性は製品によって微妙に異なります。またユーザの好みに応じて国ごとに特性を変えてある場合もあります。
これらの受像器のビデオ信号の特性の偏りは PlayStation の RGB アナログ出力からの画像ととビデオ出力からの画像を比べることによってある程度評価することができます。

出力の色合いの差は画源によって異なりますが、この差が無視できない程度であれば、γ補正の場合と同様にエンコードの段階で逆補正をかける必要があります。

表示時の色表示系とエンコード時の色表示系の違いはエンコード時の誤差（ノイズ）の評価を誤らせる原因になります。特定の色合いの画源に限って画質が変わる場合はこれが原因と考えられます。エンコードで使用している色空間では、大きな誤差として評価されなかったものが実際の表示では大きな色の違いになってあらわれるためです。

↑4 マクロブロック作成

一般的に輝度信号(Y) は色差信号(Cb,Cr) に比べて高い解像度が要求されないため、マクロブロックのCb,Cr 成分はデータが 1/4（x 方向に 1/2, y 方向に 1/2) に圧縮されます。また同時に Y 成分は４つの8x8 のブロックに分割されます。こうして 16x16 マクロブロックは、２つの色差ブロック (Cb,Cr) および４つの輝度ブロック (Y0,Y1,Y2,Y3) に分割されることになります。この 8x8 の小単位をまとめてブロックとよびます。マクロブロックは以下のように色差ブロックから順番に６個のブロックで構成されます。
色差ブロックを 1/4 に間引くには単純には以下のような方法が考えられます。

a) もとの 16x16 のブロックから x,y ともに偶数の点をのみを集めてブロックを構成する
b) もとのブロックから隣合う４点の平均をもとめてブロックの点とする

a) ではピクセルのサンプリング周波数 (fs) の 1/4 以上の成分が折り返しとなってノイズ（エイリアシングノイズ）になります。
b) では平均をとる処理が一種の２次元ローパスフィルタ (LPF) として作用するために a) よりも良好な結果が得られます。MOVCONV ではこれを採用しています。ただしこの場合でも完全に 1/4 fs 以上の成分を除去できるわけではなく、まだエイリアシングは残ります。これを改善するためにはさらに多次の遮断特性のより良いフィルタをかける必要があります。しかし、フィルタの次数が上がるほど今度はエンコード時間が増大します。目的に応じて適切な次数のフィルタを使用して下さい。

↑5 ブロックオフセット

8bit(0-255) の RGB 値で表現される色空間は YCbCr 空間では

        Y	   0～ 255
        Cb	-128～+127
        Cr	-128～+127

のレンジを持ちます。ここで、輝度ブロックと色差ブロックとのレンジを合わせるために、全ての輝度ブロックの輝度値に -128 を加算します。こうすることによって内部の処理はすべて signed charとして統一的に扱うことができます。
デコードの際には、MDEC はそのブロックが輝度ブロックか色差ブロックかを判別して、輝度ブロックであれば +128 を加算して値を元にもどす処理を行ないます。

↑6 DCT

マクロブロックを構成する各ブロックはここで DCT (Discrete Cosine Transformation)がかけられます。
DCT は一般的には直交変換とよばれる相似変換の一種です。
ブロックの各輝度値を成分とする 8x8 の行列Ｘを考えると、逆行列をもつ行列Ｐ、その逆行列 Ｐi 用いて

        Ｙ = Ｐ・Ｘ・Ｐi

の形で定義される変換を相似変換と呼びます。ここでＰの転置行列（Ｐt(x,y) = Ｐ(y,x) なる行列）をＰt とした時に
        
        Ｐi = Ｐt
がなりたつとき、この行列を直交行列とよび、この変換を直交変換と呼びます。このとき直交変換は直交行列Ｐを用いて
        
        Ｙ = Ｐ・Ｘ・Ｐt
と書けます。
DCT はこの直交変換で Ｐが以下の値を持つものです。

このとき Ｐt は以下のようになるので Ｐ・ Ｐt = Ｅが成り立ちます。（Ｅ：単位行列)

              ┌						┐
              │4096, 5681, 5352, 4816, 4096, 3218, 2217, 1130,	│

一方 DCT の逆変換 (IDCT) は Ｐ・Ｐt = Ｅ から

        Ｘ = Ｐt・Ｙ・Ｐ

と表せます。これから DCT と IDCT は行列Ｐを転置行列Ｐtに置き換えただけのものであることがわかります。

↑7 DCT の物理的意味

DCT は物理的には周波数変換としての意味を持ちます。DCT 変換で得られた 8x8 行列の左上成分 ((0,0) 成分) はもとのブロック画像Ｘの DC（直流）成分を表し、ブロック画像Ｘの全成分の平均値に等しくなります。また、他の成分は AC（交流成分）を表し右下の成分になるほど高周波成分を表します。
一般の自然画像は周波数成分が低域に集中しているため、DCT 変換を行なうと右下にいくにつれて成分の値が小さくなります。DCT による圧縮はこのような成分の偏りを利用したものです。

↑8 量子化

DCT 変換されたブロックは成分ごとに異なる分解能で量子化（クオンタイズ）されます。成分ごとの量子化の幅（ステップ）を指定するテーブルを量子化テーブル（Ｑテーブル）と呼びます。
MDEC では以下のような量子化テーブルを使用しています。
これからわかるように現在輝度ブロック・色差ブロックは、ともに同じ値を使用されています。

実際の量子化は成分ごとに対応するＱテーブルの値に、全体の量子化ステップを決める値 QUANT の積で割ることによって行なわれます。ただし DC 成分に関しては QUANT の影響を受けません。
以下に量子化の手順を示します。DC成分 (y[0]) だけはQUANTに独立に計算されている点にご注意下さい。
        
        y[0] = x[0]/iqtab[0];
        for (i = 1; i < 64; i++) 
        	y[i] = x[i]*16/(QUANT*Qtable[i]);
Ｑテーブルの値は右下にいくほど大きな値が設定されています。これは画像の低周波成分に比べて高周波数成分の精度がそれほど要求されないためです。

ここで、全体の量子化ステップ QUANT の値を大きくすると失われる情報量が増大するためデコード後の画質は劣化します。しかしブロック内の 0 成分の個数が多くなるため後述するランレベル変換時にデータを小さく抑えることができます。

↑12 VLC

VLC (Variable Length Coding) は固定辞書（コードブック）を用いてデータを可逆的に圧縮するものでハフマン符号化の原理を使用しています。ハフマン符号化は対象とするデータ（ワード：ここでは、ランレベルを指します）の出現確率の偏りを利用したもので、出現確率の高いワードから順に短い符号を割り当てることでデータの圧縮をはかるものです。

例えば、(run,level) = (0, 1) なるワードは出現頻度が高いため、01(2bit) の符号が割り当てられます。(run,level) = (23,1) は出現頻度が低いため 00000000111101 (14bit) の符号が割り当てられます。

こうしたワードと符号との対応表を辞書（コードブック）と呼びます。ハフマン符号化ではあらかじめデータの出現確率がわかっていてかつこれが時系列で変動しない（無記憶情報源）であることを仮定しています。この場合はコードブックは最初に確定でき、これを特に静的辞書と呼びます。

コードブックは画源の性質によって異なります。そのため、本来はコードブックは対象となる画源に応じて画源ごとに用意するべきものです。

しかし、繁雑さを避けるために libpress では通常の画像に当てはまるような標準的なコードブックをひとつだけ用意し、それをすべての画像に対して使用しています。ここで使用しているコードブックは典型的な自然画のランレベル分布を基準にしています。アニメーションのようにランレベルが自然画と異なる確率分布を持っている場合は別のコードブックを使用すべきです。

標準コードブックの内容を最後に添付します。右のランレベルに対応する符号が左に表されたビット列です。EOB は EndOfBlock の略で、これは NOP (0xfe00) を表します。

符号化されたデータはすでにワード（３２ビット）バウンダリは意味を持ちません。PlayStation はリトルエンディアンのバイト順序であるため、符号化されたビット列は下位ビットから順に詰められていきます。こうしてパッキングされた符号列をビットストリームと呼びます。

コードブックにないランレベルが現れた場合は、エスケープコード000001 に続きFLC(固定長符号）が続きます。FLC の (run, level) を最後に示します。

デコード時の VLC 変換はソフトウェアによって処理されます。ランレベル以降のデコード処理は MDEC によりハードウェアが行ないます。そのため、通常は VLC デコードとランレベルデコードをパイプラインで行ない処理時間を短縮します。ライブラリでは、DecDCTvlc() 関数が VLC デコードを、DecDCTin()/DecDCTout() 関数がランレベル以下の DCT 処理を行ないます。

↑14 VLCデコードの実際

ヘッダ部の後には、各マクロブロックを構成するブロックデータが、ハフマン符合化されて格納されています。 ここでは、ブロックの VLC コードのデコードの概略を示します。

ブロックの先頭ワードが
        0x061FF0D1
のブロックのデコードを考えます。ブロックデータの先頭には、DC成分（直流成分）が記録されます。一般には、ブロックの左上 (0,0) 要素の値を DC 成分と呼び、 それ以外を AC（交流）成分と呼びます。
MPEG のビットストリームは、short word の big-endian で規定されているので、 

        0x061FF0D1 = 1111 0000 1101 0001 0000 0110 0001 1111
          	      F    0    D    1    0    6    1    F

に変換されます。DC は fixed code で記録されるので、先頭の 10bit (1111 0000 11) がそのまま DC 値にになります。 この場合 MSB が 1 であるため、DC は負の値になり、 

        	1111 0000 11 = -60

DC は 10bit 有符号であることにご注意ください。
ブロックが色差ブロック(Cb/Cr ブロック）である場合、これが、そのまま DC 値になります。 しかし輝度ブロック (Y0,Y1,Y2,Y3) の場合は、この DC 成分には、オフセット 128 が加算されます。この例では DC 成分は
        	-60 + 128 = 68
になります。これが実際の先頭ブロックの DC レベルになります。輝度ブロックの場合、エンコードした画像の先頭のブロック（右上の 8x8 領域）の輝度値の平均値は、68 であることがわかります。
このオフセットは、輝度(Y) ブロックと色差ブロック (Cb,Cr) とのダイナミックレンジを (-128, 128) に合わせるためのものです。従って、色差ブロック (Cb,Cr) では、オフセットは加算されませんのでご注意下さい。
DC 成分の後にはランレベル形式の AC 成分が符号化されて続きます。

        0x061FF0D1 = 1111 0000 1101 0001 0000 0110 0001 1111

では、1111000011 に続くビットストリーム 01000 がランレベル

        (run,level) = (0,+2)

を表します。これは、最後に掲載したビットストリームとランレベルとの対応表（コードブック）を引くことでデコードできます。
以上からデコードブロックのランレベルは、

        (run,level) = (QUANT, -60), (0, 2) ....

になります。QUANT の値は BS のヘッダ部のものがそのまま使用されます。

↑16 デコード速度

MDEC の解凍速度は、最大 9000 マクロブロック／秒です。これは、320x240 の画像を秒３０枚の速度で解凍する速度に相当します。
この解凍速度は圧縮率には関係ありません。
当然ながら、画像の解像度と再生フレーム数は反比例します。
すなわち、320x240 の画像であれば、30フレーム/秒, 640x240 であれば15 フレーム／秒の動画が実現できます。

表 3 転送速度

解像度160x240320x240640x240640x480
フレーム／秒6030 15 7.5
実際は、MDEC が DCT の解凍を行なっているバックグラウンドで CPUが VLC のデコードを行なっています。従って CPU が他に重い処理を行なっている場合は、VLC のデコードがボトルネックになる場合もあります。

一方、CD-ROM は転送レートとして 150KB/sec（標準速）か 300KB/sec（倍速）を選択できます。倍速再生時は、１フレームを構成するビットストリームを 10KB (= 300KB/30) 以下に圧縮して、CD-ROM に記録すれば、CD-ROM から30フレーム／秒のデータが読み出せることになります。

動画再生レートはこれら二つの条件で決まります。例えば、倍速再生時は、１フレーム(320x240)を構成するビットストリームを 10KB(= 300KB/30) に圧縮し、CD-ROM に記録すればよいことになります。この条件を満たす範囲であれば、フレーム数・画像解像度・圧縮率は任意に選ぶことができます。

画質の向上に関して

MDEC を使用した動画の画質の向上に関しては以下のような方法が考えられます。

↑1 前処理

再生時の画質は初段、すなわち入力時の画像のノイズに最も影響されます。そのため画源は極力高画質のものを使用するべきです。
最低でも画源は、24bit のものが必要です。

画源のＳ／Ｎ比は水平方向および時間軸でのフィルタをとることで軽減できます。

高解像度キャプチャシステムが使用できるのであれば高解像度（高サンプリングレート）で一旦サンプリングを行ない、その後ローパスフィルタをかけてダウンコンバートをするべきです。２倍のオーバーサンプリングができればランダムノイズ（ホワイトノイズ）は最大 1/2に軽減できます。

また、15 フレーム／秒の再生画像を得る場合で、画源が 60 フレーム／秒のものが手に入る場合は、時間的に隣合う４枚のフレームから１枚のフレームを生成するようにします。単純に４枚のフレームの平均をとって新しいフレームを生成する場合でもノイズは最大 1/4 に低減されます。

Cb, Cr ブロックを 16x16 から 8x8 に圧縮してマクロブロックを作成する際もフィルタの係数を高次にとることでエイリアシングを除去できます。デコード時のブロックノイズ (16x16 単位で現れるノイズ）は Cb,Cr ブロックによるものです。 Cb,Cr ブロックの作成の際にとなり合うブロック同士の相関を利用することでブロックノイズの現れにくい画源を作成できます。

ブロックノイズはエンコードノイズがフレーム間で異なる値をとると視覚的に目立ちます。これは隣接するフレーム間で量子化ステップが大きく変化する場合に起こります。BS データをオーディオセクタとインターリーブして記録する場合、オーディオセクタとムービーセクタが非同期に置かれるので、フレームあたりに与えられるデータサイズが変動します。これが量子化ステップの変動につながりノイズとなって現れます。これが原因のノイズは静止部分（アニメーションの背景部分）が多い画源にみられます。こうした場合は、必ず固定セクタになるようにエンコードを行ないます。

↑2 エンコード時の評価

また家庭用の受像器では、必要以上に色差信号を強調して表示するものがあります。またγ補正が正しく行なわれていない場合もあります。これは、場合によっては、演算時に色差成分の誤差が実際以下に評価されることを意味します。色差信号は始めから 1/4 の解像度を持っていないこともありこれが原因で特定のＴＶセットで再生画質が劣化して見えることがあります。この場合はエンコード時の評価関数を工夫する必要があります。

現在使用しているコードブックは自然画を想定して決められています。従ってアニメーションのように自然画と異なる確率分布を持つ画像の場合は、圧縮率が低下します。こうした場合は、専用のコードブックを用意するべきです。現在の libpress では、コードブックを取り替えることができませんが、次回の版より対応する予定です。また、VLCエンコードはソフトウェアで行なっているためアプリケーション独自のコーディングを行なうことも可能です。

↑3 フレーム相関

フレーム相関を用いたエンコードは、フレーム落ちの処理や、デコード時の CPU 負荷を考えれば得られる結果に比べてペナルティが高いといえます。しかし、明らかに背景が固定の場面の多い画源に対しては、０次のみの相関をとることは可能です。その場合は、BS フォーマットに加えて相関を示すデータが別途必要になります。

↑4 再生時の処理

一般に 16bit モードで再生するよりも 24bit モードで再生する方が良好な結果が得られます。これは通常のエンコーダが、24bit から 16bit へ下位ビットを切り捨てる際の量子化誤差を評価関数に組み込んでいないためです。16bit で再生する場合は、入力画源を

        pix16 = (pix24+0x10)&0xfe

のように前もって 16bit に四捨五入しておくべきです。単に下位ビット切り捨てるべきではありません。
