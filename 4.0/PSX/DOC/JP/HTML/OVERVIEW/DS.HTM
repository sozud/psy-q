拡張CD-ROMライブラリ(libds)

拡張CD-ROMライブラリでは、既存のCD-ROMライブラリのカーネルを使用して、新しいインターフェイスを提供しています。なお、本章では既存のCD-ROMライブラリの知識を前提にして、主に既存のものとの相違点を説明しています。

↑ 1 概要

libdsは、libcdをベースにした新しいCD-ROM制御ライブラリです。基本システムにコマンドキューを採用し、PlayStationのメインCPUとCDサブシステムの動作速度の違いを吸収します。また、CDカバーの開閉後の処理を基本システムで行うなど、PlayStation特有の処理をライブラリで行います。

1. 1 ライブラリファイル

libdsのライブラリファイルは「libds.lib」です。各サービスを呼び出すプログラムは必ずこれをリンクする必要があります。また、libdsはCDサブシステムの制御にlibcdを使用しているため、「libcd.lib」もリンクしてください。

1. 2 インクルードヘッダ

libdsのインクルードヘッダは「libds.h」です。各種のデータ構造、マクロは全てこのファイルで定義されています。各サービスを呼び出すプログラムは必ずこれをインクルードする必要があります。

内容ファイル名
ライブラリ
libds.lib
（libcd.lib）
ヘッダlibds.h

1. 3 他のライブラリ

libdsは、一部のライブラリのバージョンに依存します。以下のライブラリは指定のバージョンをご使用下さい。

ライブラリ名バージョン

↑ 2 libdsの位置付け

2. 1 位置付け

libdsは、libcdのカーネルシステム上に実現された新しいインターフェイスです。libcdのCDサブシステムの制御ルーチンの上に独自のカーネルシステムを設け、コマンドキューの制御やCDのカバーが開けられた時の処理を実現しています。libcdで提供されていた機能と同等の機能を新規に用意していますので、プログラムを容易に移行することができます。


2. 2 libcdとの関連

libdsのカーネルシステムおよびコマンドキューは、libcdの全ての関数と排他的に動作します。libdsを使用中にlibcdの関数を呼び出すとlibdsのカーネルシステムおよびコマンドキューが破壊されます。よって、libds使用時はlibcdの関数（名前の先頭が“Cd”で始まる関数、CdInit()を含む）を使用しないでください。

2. 3 ストリーミング関数

libdsはlibcdと同時に使用できませんが、ストリーミングは従来どおりSt*()関数を使用して下さい。St*()関数はlibcd.libの一部ですがCDサブシステムをコントロールすることはないので、libdsの動作に影響を与えません。なお、ストリーミングを開始するための関数およびコマンドはlibdsで用意されているもの（DsRead2()、DslReadSコマンドなど）を使用してください。

2. 4 libapiの関数について

libapiで用意されているCDコントロールのための関数（96_init、LoadExec、Loadなど）はlibdsのシステムが動作している時に使用することはできません。これらの関数を使用する場合は、libdsのシステムを終了させてから使用してください。

↑ 3 libcdとの相違点

3. 1 プリミティブコマンド

プリミティブコマンドはlibcdと同じ機能が使用できます。コマンドコードは、libds.hで再定義され、シンボルの先頭の３文字“Cdl”が“Dsl”に置き換えられています。

3. 2 構造体

libcdで用意されていた全ての構造体については、libdsでも同じ機能を持つものが用意されています。構造体についてもシンボルの先頭３文字“Cdl”が“Dsl”に置き換えられています。

3. 3 関数

関数は、libcdで用意されていたものと同等の機能を持つ関数がlibdsでも用意されています。シンボルの先頭２文字を“Cd”から“Ds”に置き換えることでlibdsで用意されている関数となります。ただし、引数や動作タイミングなど異なる場合があります。各関数についての詳細はリファレンスを参照してください。

3. 4 処理速度

libdsではプリミティブコマンドの管理にコマンドキューを使用しています。よって、厳密な処理速度（タイミング）はlibcdと異なります。
libcdでプリミティブコマンドを発行した場合、前のコマンドが実行中であればコマンド発行のための関数（CdControl()など）はそのコマンドの終了を待ち、目的のプリミティブコマンドを発行します。この間はCPUの処理はブロックされます。
これに対してlibdsでは、コマンド発行時に他のコマンドが実行中であればそのコマンドはコマンドキューに登録され、コマンド発行のための関数はその時点で終了します。キューに登録されたコマンドは前のコマンドの終了時またはVSync毎に実行可能かどうか判定され、可能であればCDサブシステムに送られます。この方式のメリットは、CDサブシステムの状態に関わらずコマンド発行でCPUの処理がブロックされないところにあります。また、一度に複数のコマンドを発行する場合でもそれぞれのコマンドの終了を待たずに次のコマンドを発行（登録）することができます。

3. 5 互換関数

libdsにおけるプリミティブコマンドの実行は全てノンブロック型で行われますが、libcdのCdControl（CdControlB）に対応する関数も用意されています。

↑ 4 初期化と終了

4. 1 システムの初期化

libdsを使用する場合は、プログラムの先頭でDsInit()を実行します。

        int DsInit( void );

DsInit()はResetGraph()およびPadInit()の後でコールしてください。DsInit()実行後はCDサブシステムの管理をlibdsのシステムが行うため、libds以外の環境（libcdやlibapi）からCDサブシステムをコントロールすることはできません。
また、DsInit()は内部でlibcdの初期化も行いますので、ストリーミングライブラリ（St*()関数）を使用する場合でもCdInit()を呼ぶ必要はありません。

4. 2 初期化後のリセット

DsInit()でシステムを初期化した後に再びDsInit()をコールすると、トラブルの原因となります。通常の用途でシステムをリセットしたい場合は、DsFlush()を使用してください。

        void DsFlush( void );

DsFlush()はCDサブシステムをフラッシュし、コマンドキュー（後述）をクリアします。
もし何らかの理由でシステムを最初の状態に戻したい場合は、DsReset()を使用してください。

        int DsReset( void );

DsReset()を使用すると、プログラムで設定したコールバック関数もクリアされますので、リセット後に設定し直してください。

4. 3 システムの終了

子プロセスを起動したりオーバーレイを行う場合は、libdsのシステムを一度終了させてください。システムを終了させるためにはDsClose()を使用します。

        void DsClose( void );

なお、子プロセスの実行が終了し再び処理を再開する場合はDsInit()をコールしてください。

4. 4 注意

DsFlush()、DsReset()、DsClose()ではデータリード（再生）動作を中止しません。データリード（再生）動作はプログラムからDslPauseを発行して明示的に止める必要があります。これらの関数を使用する前にDslPauseを発行してください。

        	:
        while( DsControlB( DslPause, 0, 0 ) == 0 );
        DsClose();
        	:

データリード（再生）が行われたままシステムを終了し、LoadExec等を行った場合は誤動作する可能性があります。

↑ 5 コマンドキュー

コマンドキューとは、CDサブシステムの状態を監視し、プリミティブコマンドの発行と終了を管理するシステムです。発行されたコマンドはキューに積まれ、CDサブシステムがコマンドを受け付けることが可能になった時点でサブシステムに送られます。
また、コマンドキューはCDサブシステムの仕様上必要な処理を自動的に行います。例えばカバーが開けられたときの処理は、システムで自動的に行われます。この間はコマンドをCDサブシステムに送ることはできませんが、キューにコマンドを登録しておけば処理終了後に直ちにコマンドが発行されます。

5. 1 コマンドの発行

コマンドキューにプリミティブコマンドを発行するためにはDsCommand()関数を使用します。

        int DsCommand( u_char com, u_char* param, DslCB func, int count );
        	com		コマンドコード
        	param		コマンドに対するパラメータ（４バイト）
        	func		コマンド終了コールバック関数のポインタ
        	count		リトライ回数（-1で無限回リトライ）

第３引数は、コマンド終了時に呼び出されるコールバック関数のポインタです。このコールバック関数はコマンド毎に設定することが可能で、対応するコマンドの終了時にのみ呼び出されます。
コマンドの発行（キューへの登録）が成功すると、返り値としてコマンドID（>0）が渡されます。コマンドの実行状況や結果を得る場合は、このコマンドIDを使用します。
なお、コマンドキューがいっぱいになった場合は０が返されます。

5. 2 終了確認

コマンドキューに登録されたプリミティブコマンドの終了確認を行うためには、コマンド発行時に設定するコールバック関数を使用するか、DsSync()関数を使用します。

        int DsSync( int id, u_char* result );
        	id		コマンドID
        	result		コマンドに対する返り値（８バイト）

DsSync()は呼び出された時点でのコマンドの実行状況を返します。

シンボル内容
DslCompleteコマンドは正常終了した。
DslDiskErrorコマンドはエラーとなった。
DslNoIntrコマンドはまだ実行されていない。
DslNoResultコマンドは終了しているが結果が残っていない。


実行が終了していた場合（DslComplete、DslDiskError）はresultに返り値が格納されます。
システムには複数の実行結果が保存されます。よって、２つ前に実行されたコマンドの結果を得ることもできます。ただし実行結果は古い順に上書きされていきますので、あまり古いコマンドについてはDsSync()の返り値がDslNoResultとなります。システムで保存される実行結果の数はマクロ定数DslMaxRESULTSに定義されています。

5. 3 コマンドキューの状態確認

コマンドキューに現在いくつのコマンドが積まれているのかを得るにはDsQueueLen()関数を使用します。

        int DsQueueLen( void );

DsQueueLen()は現在キューに登録されているコマンドの数を返します。コマンドの数には現在実行中のものも含まれます。また、キューに登録できるコマンドの最大数はマクロ定数DslMaxCOMMANDSに定義されています。コマンドの最大数はライブラリのバージョンアップにともなって変更される可能性がありますので、必ずマクロ定数で参照してください。

システムの状態を得るにはDsSystemStatus()を使用します。

        int DsSystemStatus( void );

DsSystemStatus()はシステムが現在どのような状態にあるかを返します。リターン値は以下の通りです。

        DslReady	コマンド実行可能状態
        DslBusy		コマンド実行中、もしくはコマンドが実行できない状態
        DslNoCD		CDがセットされていない

DslReadyは、CDサブシステムが正常な状態にあり、何もコマンドが実行されていない場合です。この時にコマンドをキューに発行するとすぐに処理が開始されます。なお、タイミングを重視する場合は念のためにキューのコマンドの数が０であることをあわせて確認してください。
DslBusyは、現在コマンドが実行中であるか、何らかの理由でコマンドが実行できない状態になっている場合です。コマンドが実行できない状態とは、カバー開閉後の処理を行っている、もしくはCDの回転速度が変更されて一定期間処理ができない状態を指します。この間はコマンドはキューに積まれ、状態が改善された時点でCDサブシステムに送られます。
DslNoCDはドライブにCDがセットされていない場合です。カバー開閉後の処理でCDが認識できなかった場合にDslNoCDに移行します。この状態は再度カバーが開けられてCDがセットされるまで変わりません。

5. 4 処理タイミング

DsCommand()によって発行されたプリミティブコマンドは、実行可能であればすぐにCDサブシステムに送られます。前のコマンドが終了していないなど実行可能でなければキューに積まれますが、コマンドが終了次第（syncコールバックの中で）発行されます（syncチェイン）。
カバーの開閉など処理がブロックされた場合はsyncチェインは切れますが、この場合はVSyncの割込みでキューがポーリングされます。

5. 5 エラー発生時の動作

コマンド実行中にエラーが発生した場合は、そのコマンドは再発行（リトライ）されます。コマンドを何回まで実行するかは、第４引数countで指定します。リトライはcount回行われます。count == 0の場合はリトライは行われません。なお、count == -1の場合はそのコマンドが成功するまでリトライ（無限リトライ）されます。指定回数だけリトライしても成功しなかった場合は、そのコマンドはエラーとなり、キューより取り除かれます。
また、CDカバーが開けられた場合はキューに登録された全てのコマンドがキャンセルされます。この場合、コマンドにコールバック関数が設定されていれば各コールバック関数がキューに積まれている順番にキックされます。

5. 6 コールバック

プリミティブコマンドが終了した場合のコールバック関数の設定方法には、各コマンドに設定する方法と共通のコールバック関数を設定する方法の２つがあります。
各コマンドにコールバック関数を設定した場合は、そのコマンドの終了以外では関数呼出しは行われません。またコマンド終了後はコールバック関数の設定は自動的に解除されます。
共通コールバックを設定した場合は、全てのコマンドの終了時と、非同期（CDカバーが開けられたときなど）に発生するエラー時にキックされます。

5. 7 複数の処理について

コマンドキューには複数のコマンドを一度に登録することができますが、これは複数の処理（データリードや再生）を一度に発行できるということではありません。データリードコマンド（DslReadN、DslReadS）および再生コマンド（DslPlay）は、処理としてはコマンドがCDサブシステムに受理された時点で終了となります。コマンドキューはこの終了によってリード（再生）コマンドをキューから削除し、次に何らかのコマンドがあった場合はそのコマンドをCDサブシステムに発行します。次に発行されたコマンドによってはデータリード（再生）処理は中止されますので、目的のデータが得られないことになります。
よって、コマンドキューのレベルでは複数のデータリード（再生）処理を一度に登録することはできません。複数のデータリード（再生）処理を行う場合は、それぞれの処理に対応するコマンドを発行し、必要な量のデータを読み出して（必要な時間再生を行って）から次のコマンドをキューに発行してください。

↑ 6 コマンドパケット

コマンドパケットとはコマンドキューにプリミティブコマンドを発行する方法の一つで、CDのデータリード（CD-DAの再生）のための一連のコマンドをまとめて発行します。データリード（再生）を行うためには、
  • ポーズ（前の処理を確実に終わらせるため）
  • 動作モードの設定
  • 先頭ポジションの指定
  • リード
の４つのプリミティブコマンドを発行する必要があります。これらの４つのコマンドを１回の関数呼出しでキューに登録することができます。
コマンドパケットとしてコマンドを発行することで、安定したCDアクセスを行うことができます。コマンドパケットでは動作モードと先頭ポジションを毎回指定しますので、その前CDサブシステムの状態に左右されません。また、エラー時のリトライも先頭から行うため、リトライの成功率が高くなります。

6. 1 コマンドパケットの発行

コマンドパケットを発行するにはDsPacket()を使用します。

        int DsPacket( u_char mode, DslLOC* pos, u_char com, DslCB cbsync, int count );
        	mode		動作モード
        	pos		先頭ポジション
        	com		リード（再生、シーク）コマンド
        	cbsync		コマンド終了コールバック関数のポインタ
        	count		リトライ回数（-1：無限リトライ）

この関数を実行すると、キューに以下の４つのコマンドが登録されます。
  • DslPause 0
  • DslSetmode mode
  • DslSetloc pos
  • comで指定されたコマンド 0
comにはDslPlay、DslReadN、DslReadSのいずれかのコマンドを指定することができます。
また、comにシークコマンド（DslSeekL、DslSeekP）を指定すると、シークの終了までをパケットとすることができます。これにより、先行シークなどを行うことができます。

6. 2 終了確認

コマンドパケットの終了を確認するためには、発行時にコールバック関数を指定するかDsSync()を使用します。コマンドパケットは、展開された全てのプリミティブコマンドの実行が終了した時点で終了します。DsSync()で確認する場合は、プリミティブコマンドと同じようにコマンドIDで参照してください。resultには、最後のプリミティブコマンドの実行結果が格納されます。

6. 3 処理タイミング

コマンドパケットは、展開されたプリミティブコマンドがコマンドキューによって処理されます。よって、処理タイミングはコマンドキューの動作に準じます。

6. 4 エラー時の動作

パケット中のコマンドがエラーとなった場合もリトライが行われますが、普通のコマンド（DsCommand()で発行したもの）と異なり、リトライはパケットの先頭のコマンドから行われます。これは成功率の高いリトライを行うためで、データリード（再生）に関しては一つずつコマンドを発行するよりもパケットとして発行されることを推奨します。
リトライを行う回数はcountで指定します。普通のコマンドと同じくcount == 0ではリトライを行わず、count == -1で無限リトライです。リトライ回数を超えてエラーが発生した場合はパケットはキューから取り除かれます。

↑ 7 簡易コールバック

CDからデータを読み出す場合は、データリードコマンドを発行し、発生するデータレディ割込み毎にデータをCDのセクタバッファからメインメモリに転送する処理を行いますが、データレディ割込みのハンドリングを容易に行う機能が簡易コールバックとしてライブラリで提供されます。

7. 1 簡易コールバックの機能

簡易コールバックはデータレディ割込みにフックされます。割込みで行う処理のうち、データが正常に読み込めた場合はアプリケーションで記述します。ライブラリではエラーが発生した場合のリカバリー処理を行います。
簡易コールバックを使用するには、DsStartReadySystem()を呼び出します。

        int DsStartReadySystem( DslRCB func, int count );
        	func		データリード成功時のコールバック関数のポインタ
        	count		リトライ回数（-1：無限リトライ）

コールバック関数は、基本的にデータが正常に読み込めた場合にのみキックされます。エラー時のリカバリーはシステムで自動的に行われます。
countはリトライの回数を設定します。count == -1で無限リトライとなります。リトライ回数を超えてエラーが発生した場合は、コールバック関数がDslDiskErrorでキックされます。

DsStartReadySystem()は、対応するリードコマンド（パケット）の終了コールバック内で、コマンドの成功を確認して呼び出してください。これより早いタイミングで呼び出すと、エラーリカバリーが誤動作する可能性があります。現在のCD-ROMシステムではコマンドに対するエラーとそれ以外のエラーの区別がないため、簡易コールバックのシステムがコマンドのエラーに反応してしまうためです。また、システムの開始が遅れると先頭セクタを取りこぼす可能性があります。

7. 2 リカバリー時の挙動

リードの途中でエラーが発生すると、簡易コールバックシステムはリカバリーを行います。リカバリーは、システムに保存されている情報（最後に発行したコマンド、最後に設定された動作モード、最後にシークされた位置、現在の位置など）を元にコマンドを発行し直すことで行われます。

リカバリーの際のシーク位置はシステムによって決定されます。再開されたリードは、エラーが発生したセクタの手前から行われますが、funcで設定したコールバック関数は前回成功したセクタの次のセクタが読み出されるまでキックされません。例えば最初のリードで４セクタ目でエラーが発生した場合、既に３セクタまでの処理は終了しているわけですが、リカバリーが行われて再び４セクタ目のデータが読み出されたときにコールバック関数がキックされます。

        １回目	１、２、３、（４）
        	            ↑ここでエラー（コールバックはキックされない）
        	リカバリーで手前にヘッドが戻される
        ２回目	．．．．．．４、５、６
        	            ↑このセクタからコールバック関数がキックされる

7. 3 コールバック関数の記述

データリード時にキックされるコールバック関数は、以下の書式で記述します。

        void function( u_char intr, u_char* result, u_long* subhead );

intrおよびresultは通常のデータレディコールバック関数と同じように割込みの情報が参照されます。簡易コールバックでは、ほとんどの場合はintr == DslDataReadyもしくはintr == DslDataEnd（DA再生時のみ）です。intr == DslDiskErrorとなるのは、
  • リトライ回数を超えてエラーが発生した場合
  • 途中でCDカバーが開けられた場合
です。この時のリカバリーはアプリケーションで記述する必要があります。

データリードが成功してコールバック関数がキックされたときには、データのサブヘッダの転送は終了しています。これは、システム側でサブヘッダを見てデータの確認を行っているためですが、セクタバッファのポインタはデータの先頭に移っていますので、すぐにデータ本体の転送を行うことができます。データ本体の大きさは2048bytesです。

7. 4 システムの終了

目的のデータがリードできた場合は、簡易コールバックを終了させてください。簡易コールバックを終了させるにはDsEndReadySystem()を使用します。

        void DsEndReadySystem( void );

システムの終了は、最後のセクタを読み込んだ直後に行う必要があります。終了が遅れるとリードが進み、余分なコールバックが発生してメモリを破壊することが考えられます。よって、最後のセクタを転送したコールバック関数の中で終了するようにしてください。

7. 5 注意点

簡易コールバックを使用してデータリードを行う場合は、動作モードの設定でセクタサイズを2340bytes（DslModeSize1ビットをON、DslModeSize0ビットをOFF）にしてください。

8. 1 CDカバーの開閉

PlayStationのCD-ROMドライブでは、途中でCDカバーの開閉が行われると特殊な処理を必要としていましたが、libdsではこの処理をシステムで行います。
CDカバーが開けられるとシステムはビジー状態（DslBusy）に移行し、ユーザーからのコマンドの発行をブロックします。カバーが閉じられるとシステムはディスク再認識のための処理を行い、レディ状態（DslReady）に戻ります。
CDカバーが開けられたとき実行されていた処理はエラーとなります。また、コマンドキューに登録されている全てのコマンドが削除されます。よって、システムがレディ状態となるのを待って処理をやり直してください。なお、CDカバーの開閉処理が終了した直後は動作モードおよびヘッドの位置は初期化されていますので、これをふまえた処理のやり直しを行ってください。

8. 2 CDの入れ替えに関する注意点

実行中にCDの入れ替えを行う場合、カバーの開閉に関する処理はシステムで行われます。ただし、セットされたCDの種類の認識は行いませんので、アプリケーション側で行う必要があります。
libdsライブラリでは、libcdで提供されていたCdDiskReady()までの処理を自動化しています。よってシステムのステータスがDsSystemStatus() == DslReadyとなった後にCDの種類を認識するようにしてください。なお、libcdで用意されていたCDの種類を得るための関数と同等の関数DsGetDiskType()も用意されています。関数についてはリファレンスを参照してください。

libdsで推奨されるCDの入れ替え手順は以下の通りです。
  1. CDの回転を止める。
  2. 入れ替えメッセージを出力する。できれば入れ替え終了時にボタン入力で確認を取る。
  3. DsStatus()で最新の結果をポーリングし、カバーが開けられた（DslStatShellOpenビットが立つ）ことを確認する。
  4. DsSystemStatus() == DslReadyとなるのを待つ。
  5. DsGetDiskType()でCDの種類を調べ、PlayStationディスクであることを確認する。
  6. 目的のディスク（他のゲームのディスクではないか、何枚目のディスクかなど）かどうかを確認する。
手順４でDslNoCDが返された場合は、ライブラリでCDがセットされていることが確認できなかった（一定時間内にCDのスピンドルが回らなかった）ことを示します。「CDが認識できません」などのメッセージを出力し手順２に戻ってください。手順５でPlayStationディスクと確認できなかった場合も同様にメッセージを出力し、手順２に戻ります。
なお、手順２でボタン入力で確認を取るようにした場合は手順３は省いてもかまいません。また、手順６の確認はディスクの特定の位置に特定のデータを書くなど各アプリケーションで確認方法を設定してください。

8. 3 先行シーク

プログラムで、次にリードするデータファイルが決まっている場合に前もってファイルの先頭までシークを行っておくことで、データリードにかかる時間を見かけ上短縮することができます。コマンドパケットでシークを行うとエラー時のリトライも自動化されますので、メインフローの負担は最小になります。状況によって異なりますが、先行シークを行えばデータリード時の所用時間は約０．４秒ほど短縮されます。
またゲームの進行に合わせてXAオーディオを再生する場合などは、先行シークを行うことでタイミングが合わせやすくなります。

8. 4 複数ファイルの連続リード

データの切り替えで複数のデータファイルをリードする必要がある場合、ロード時間を短縮するにはシークを減らすことが最も効果的です。シークを減らすには、データファイルを連続してCDにレイアウトし、１回のリードで複数のファイルを読み込みます。シークを１回減らすことで約０．４秒の短縮ができますので、５回減らすとロード時間が２秒短縮されます。
各ファイルのメインメモリ上の転送先が異なる場合はリードの途中で転送アドレスを切り替える必要がありますが、簡易データコールバックを使えば実現が容易になります。libdsのサンプルに簡易データコールバックを使用して実現したものがありますので、こちらも参照してください。

8. 5 外周３分問題

現在のCD-ROMサブシステムでは、CD-ROMの外周３分以内へシークする場合、シーク開始地点によっては、正しくシークが行なわれない場合があります。
この現象を回避するために以下のいずれかの方法をとる必要があります。
  • 最外周３分（データの最後の３分）にダミーデータを入れておく（ダミーデータは使用しない）。
  • BGMなどにCD-DAを使用する場合、最終曲を３分以上にする。この場合は、曲の途中から再生したり、曲の途中でリピートをかけない限り、最外周３分へのシークは発生しません。従ってCD-ROMサブシステムは正常に動作します。
  • どうしても最外周３分をデータエリアとして使いたい場合は、外周３分以上は連続した１つのファイルとしてアクセスする（オープニング、エンディングのムービに使用するなど）。
なお、ここで言う外周とはディスクの物理的な外周ではなく、データ（DA）が記録された領域の最外周のことです。

8. 6 DslPlay、DslReadN、DslReadSの注意点

現在のCD-ROMシステムでは、コマンドDslPlay、DslReadN、DslReadSはコマンドコードをCDサブシステムが受理した時点でコマンドとしての処理を終了し、DslCompleteを返すようになっています。ただし、実際はその後も処理を継続しており、この処理でエラーが発生することがあります。
        発行．．．．成功．．．．．．．．．．シーク完了．．．．（データリード）．．．
                                      ↑この段階でエラーになることがある

このエラーは割込みとして報告されますが、コマンドとの対応は取れていませんので（コマンドの処理としては最初のCompleteで終了したとみなされる）キューのリトライ対象となりません。そのため、このエラーについてはアプリケーション側で対応する必要があります。
このエラーは、各コマンドに設定できるコールバック関数には反映されません。このエラーが報告されるコールバックはデータレディコールバック（DsReadyCallback()で設定）とコマンドに独立なsyncコールバック（DsSyncCallback()で設定）の２つです。エラーをリカバリーするためには、これらのコールバックの中にエラーリカバリールーチンを用意するか、データリードが開始されるまでステータスをポーリングしてください。DsSync()の引数idを-1にすると、コマンドと対応が取れないエラーの実行結果を得ることができます。また、データリードが開始されたことを確認するにはDsStatus()を使用します。

以下にポーリング型のエラー対応例を示します。なお、この例ではリードが開始されるまで処理がブロックされてしまいます。これを防ぐためにはリード開始を待つルーチンを１フレームに１回呼ぶなどの工夫が必要です。

        		:
        		:
        /* リードコマンドをパケットで発行（無限リトライ）
            これが成功するまではシステムでリトライが行われる */
        DsPacket( DslModeSpeed | DslModeSize1, &pos, DslReadN, 0, -1 );
        
        /* リード開始を待つ */
        while( ( DsStatus() & DslStatRead ) == 0 ) {
        	/* id == -1で見つかるエラーはシステムで対応されていない */
        	if( DsSync( -1, result ) == DslDiskError ) {
        		/* リトライを行う
        		   この例ではパケットの再発行で対応する */
        		DsPacket( DslModeSpeed | DslModeSize1, &pos, DslReadN, 0, -1 );
        	}
        }
        		:
        		:

データレディコールバックを使用した場合は、以下のようになります。

        		:
        		:
        	/* パケット発行時にsyncコールバック関数を設定しておく */
        	DsPacket( DslModeSpeed | DslModeSize1, pos, DslReadN, cbsync, -1 );
        		:
        		:
        }
        		:
        /* パケットのsyncコールバック関数
           処理が成功した場合にデータレディコールバックをフックする */
        void cbsync( u_char intr, u_char* result )
        {
        	if( intr == DslComplete ) {
        		/* ここでレディコールバックをフックすることで、
        		   コマンドに対するエラーと混同するのを防ぐ */
        		DsReadyCallback( cbready );
        	}
        }
        		:
        		:
        /* レディコールバック関数
           データ転送に使うが、エラー時のリカバリーを持たせる */
        void cbready( u_char intr, u_char* result )
        {
        	if( intr == DslDiskError ) {
        		/* コールバックをクリアしておいてから・・ */
        		DsReadyCallback( 0 );
        		/* パケットを再発行する */
        		DsPacket( DslModeSpeed | DslModeSize1, pos, DslReadN, cbsync, -1 );
        		return;
        	}
        	if( intr == DslDataReady ) {
        		/* データ転送ルーチン（省略） */
        	}
        }

この場合に注意すべきことは、データレディコールバックには全てのエラーが報告されてしまうということです。コマンド発行に対するエラーも報告されてしまうため、コールバック関数を割込みにフックするタイミングは気を付ける必要があります。この例では、パケットの成功時にフックされるようになっています。また、この方式を取った場合はリードが終了した場合にすぐにデータレディコールバックを外すようにしてください。これを忘れると意図されない場所でリードのパケットが発行されてしまいます。

なお、簡易コールバックではこのエラーについて対応を行っていますので、アプリケーション側でこの対策を取る必要はありません。

8. 7 データリードの終了について

CDのデータをリードするためにコマンドを発行し、データレディコールバックでデータの転送を行うシステムをアプリケーションで構成する場合、リードの終了処理にコツがあります。
リードを終了する場合、コマンドDslPauseを発行することで動作は停止しますが、コマンドがCDサブシステムに受理されて動作が停止するまでの間に１、２セクタ余分にリードしてしまうことがあります。データレディ割込みにフックされたコールバック関数によっては、この余分なデータをメインメモリに転送してしまい、データを破壊する可能性があります。これを防ぐためには、目的のセクタ数をリードしたら直ちにコールバック関数を割込みから外してください。コールバック関数を外すには、引数0でDsReadyCallback()を呼び出します。コールバック関数を外すことで、余分なセクタが読み出されても、メインメモリに転送されなくなります。その後でDslPauseを発行してリード動作を停止させてください。
