                                                 Library Overview Release 4.0

拡張グラフィクスライブラリ(libgs)
==================================

  拡張グラフィックスライブラリ(libgs)は、基本グラフィックス、基本ジオメトリの
  両ライブラリを使って３次元グラフィックスシステムを構築したものです。ここで
  扱われるデータはオブジェクト、バックグラウンド面など、より大きな単位となり
  ます。

 1 概要
--------

    libgsは拡張グラフィックライブラリと呼ばれlibgpu/libgte上に構築された3Dグ
    ラフィックス(ポリゴン等)と2Dグラフィックス(スプライト/BG（背景面）等)を統
    合的に扱うことのできるグラフィックスライブラリです。
    libgsで扱うモデルフォーマットはTMDフォーマットと呼ばれるもので複数オブジ
    ェクト、スケール情報、テクスチャアドレス情報などがlibgsでデコードするため
    の最適な状態で格納されています。
    libgsで扱う画像データフォーマットはTIMフォーマットと呼ばれるもので画像の
    解像度、色数、カラールックアップテーブル情報などがピクセルデータと共に格
    納されています。
    TMDフォーマット及びTIMフォーマットはPlayStationオーサリングツールの標準フ
    ォーマットであるためオーサリングツールで作られたデータはそのままlibgsで利
    用することができます。
    libgpu/libgteがポリゴンレベルのデータを処理するライブラリであるのに対し
    libgsはオブジェクトという複数のポリゴンをまとめた単位でデータを処理するた
    め簡単に３次元のプログラムをプロトタイピングできます。
    そしてオブジェクトに付加されたアトリビュートを用いていろいろな特殊効果を
    作り出すことができます。
    ただしlibgsは扱う入力フォーマットを限定しているためlibgpu／libgteで最適化
    されたプログラムに比べるとオーバヘッドはあります。
    そのため実際のゲーム製作では、一部分をlibgpu／libgteのレベルで作成する必
    要もあります。
    しかし、libgsはオープンなアーキテクチャであり、低レベルライブラリを用いて
    開発された、ユーザのモジュール単位を追加して拡張することができます。

  1.1 ライブラリファイル

    拡張グラフィックスライブラリのファイル名は「libgs.lib」です。
    各サービスを呼び出すプログラムは、必ずこれをリンクする必要があります。

  1.2 インクルードヘッダ

    拡張グラフィックスライブラリのインクルードヘッダは「libgs.h」です。各種の
    データ構造、マクロはすべてこのファイルで定義されています。各サービスを呼
    び出すプログラムは、必ずこれをインクルードする必要があります。

        表 1
    +----------+----------+
    |内容       ファイル名|
    |ライブラリ libgs.lib |
    |ヘッダ     libgs.h   |
    +----------+----------+
    

  1.3 libgsの機能

    libgsで実現されている機能には、以下のものがあります。
         ・階層座標系
         ・光源計算（３光源デプスキューイングアンビエント）
         ・オブジェクトの自動分割 半透明処理
         ・視点制御
         ・Zソート処理
         ・OTの初期化階層化圧縮
         ・フレームダブルバッファ
         ・アスペクト比の自動調整
         ・２Dクリッピングオフセット処理
         ・スプライト／BG／ライン
         ・libgpu,libgteとの共存

 2 座標系
----------

    libgsの座標はGsCOORDINATE２と呼ばれています。
    座標系はワールド座標系を最上位とする階層があり下の階層から上の階層へとワ
    ールド座標系に到達するまで積算されます。
    GsCOORDINATE2は 座標系を記述するためのパラメータと座標計算を高速化するた
    めのワークエリアからなります。
    座標系はMATRIX型のパラメータにより記述されます。
    MATRIXパラメータはその座標系の親の座標系からその座標系への変換パラメータ
    となります。
    座標系の空間の大きさはXYZともに符合つき３２ビットです。

  2.1 座標系の初期化

    座標系の初期化にはGsInitCoordinate2()を使います。
    GsInitCoordinate2()はGsCOORDINATE2の各パラメータを初期化するだけなのでプ
    ログラマがGsInitCoordinate2()を使わずに初期化しても構いません。
    パラメータは書き換えられた瞬間から有効になり計算に使われます。

  2.2 回転／平行移動の順番

    座標系に設定されるパラメータの回転と平行移動の順番は
      	回転 → 平行移動
    になります。
    またRotMatrix()を使って回転マトリックスを生成しそれをGsCOORDINATE2に設定
    した時は回転順は
      	Z → Y → X
    の順になります。

  2.3 フラグのクリア

    階層座標系からローカルワールドマトリックスを求めるに際して高速化を行なっ
    ています。
    計算済みの座標系には構造体GsCOORDINATE2のメンバのflagに１を設定し結果を
    workmに格納しています。そのためGsCOORDINATE2のパラメータを書き換えた時は
    flagを０にクリアしないと再計算が行なわれずworkmの内容が使われてしまうので
    必ずクリアする必要があります。
    ただし親座標の変更はその親座標にリンクしている子座標には自動的に伝搬され
    るため子座標のフラグまでクリアする必要はありません。

  2.4 座標系設定のサンプル


    平行移動

        GsCOORDINATE2	sample_coord;	/* 平行移動を設定する座標系 */
        int x,y,z;			/* 平行移動量 */
        
        sample_coord.coord.t[0] = x;
        sample_coord.coord.t[1] = y;
        sample_coord.coord.t[2] = z;

    回転

        GsCOORDINATE2	sample_coord;	/* 回転を設定する座標系   */
        SVECTOR		rot;		/* 設定する回転角 (x,y,z) */
        MATRIX		tmp1;		/* 求める回転マトリックス */
        
        RotMatrix(&rot,&tmp1);		/* 回転ベクトル→回転マトリックス変換
        				 RotMatrix()を使うと回転順はzyxとなる */
        sample_coord.coord = tmp1;

 3 オブジェクト
----------------

    libgsでは３DオブジェクトハンドラとしてGsDOBJ2 GsDOBJ3 GsDOBJ5の３種類のタ
    イプを用意しています。
    ここでは基本的なオブジェクトタイプであるGsDOBJ2を取り上げて説明します。
    オブジェクトを操作するためにはGsDOBJ2のメンバのcoord2およびアトリビュート
    (attribute)を使います。
    coord2は座標系（GsCOORDINATE2へのポインタでありオブジェクトの位置を制御す
    る時にポイントされる座標系のパラメータを設定します。
    attributeはオブジェクトの属性をあたえます。
    属性には表示／非表示などの一般的なものから光源計算の方法の切替えなどの特
    殊効果などがあります。

  3.1 オブジェクトの初期化

    GsDOBJ２でオブジェクトをハンドルするためには 読み込まれたTMDデータとハン
    ドラとをリンクする必要があります。
    TMDデータとのリンクはGsLinkObject4()を用います。GsLinkObject4()はTMDデー
    タの何番目のオブジェクトとGsDOBJ２とをリンクするのかを設定します。

  3.2 オブジェクトの位置の制御

    オブジェクトの位置を制御するには構造体GsDOBJ２のメンバのなかのcoord2でポ
    イントされる座標系GsCOORDINATE2のパラメータを設定します。
    GsCOORDINATE2のsupterがWORLDの時はその座標系はワールド座標系と等価なため 
    設定された位置パラメータはワールド座標系の位置になり回転パラメータはワー
    ルド座標系の原点を中心とする回転となります。

  3.3 オブジェクトの動きの階層構造

    オブジェクトの動きに階層構造を定義したい場合は、GsDOBJ２のメンバのcoord2
    がポイントする座標系の階層を定義することで可能です。
    例えばobject1がcoordinate1をポイントしobject2がcoordinate2をポイントして
    いる時、object1をobject2の親にするためにはcoordinate2のsuperにcoordinate1
    を設定します。
    
        図 1 階層構造化

    このように定義すれば、object2の動きはobject1に連動します。
    object1の動きはobject2に連動しません。
    objcet1,object2を動す時はcoordinate1に位置を設定します。
    object2だけを動かす時はcoordinate2に設定します。

  3.4 オブジェクトのattribute制御

    GsDOBJ2にはattributeのフィールドがありそのビットを操作することで
    様々な効果をオブジェクトに与えることができます。

   (1) マテリアル減衰

      光源計算を行なう際に、方線の傾きと輝度の減衰の関係を設定します。
      ０～３迄の値をとり３がもっとも減衰がきつくなります。
      このパラメータによってオブジェクトの材質感を変えることができます。
      減衰の値を大きくすると計算時間はそれだけかかります。
      光源計算でmaterial lightingを有効にしないとこのパラメータは無視されます。
      ただし現在のバージョンではまだサポートされていません。

   (2) 光源モード

      光源計算の方式を決定します。
      デフォルトの方式はGsSetLightMode()によって設定されます。
      このアトリビュートはオブジェクト毎に光源計算の方式を制御したい時に設定
      します。

   (3) 光源計算OFF

      光源計算を強制的にキャンセルするためのビットです。
      光源計算の有りのTMDもこのビットをたてると光源計算をキャンセルでき高速に
      なります。

   (4) ニアクリップ

      ポリゴンの端点が非常に接近した場合、（Z<h/2ただしhはプロジェクション）
      透視変換時にオーバフローを起こしたポリゴンを単純にクリップせず、形をゆ
      がめてでも強引に表示したい場合に設定します。
      ただし現在のバージョンではまだサポートされていません。

   (5) バッククリップ

      ポリゴンは頂点の順番によって表裏があります。
      凸物体の場合は裏を表示する必要がないため、デフォルトでは裏向きポリゴン
      はクリップされますが、このアトリビュートによって裏向きポリゴンも表示さ
      せることができます。ただし現在のバージョンではまだサポートされていませ
      ん。

   (6) 半透明レート

      半透明には通常の半透明の他に３種類のモードがあります。１００％加算、減
      算２５％加算です。それらのモードを制御します。

        表 2 半透明レート
    +--+----------+------------------+
    |値 背景輝度値 プリミティブ輝度値|
    |0  0.5        0.5               |
    |1  1.0        1.0               |
    |2  1.0        -1.0              |
    |3  1.0        0.25              |
    +--+----------+------------------+
      
      テクスチャマッピングされたポリゴンを半透明にするにはテクスチャの色のフ
      ィールド（ダイレクトカラーの時はテクスチャパターン、インデクスカラーの
      時はCLUTのフィールド）の最上位ビット（STPビット）をたてる必要があります。
      STPビットを利用して ピクセル単位の半透明の処理が可能です。

   (7) 表示制御

      その物体を表示するか、表示しないかを制御します。
      表示しない場合は、計算対象からも外され負荷は軽くなります。

   (8) 自動分割

      実行時にオブジェクト単位でそのオブジェクトに含まれる全てのポリゴンを分
      割する機能です。分割数は2x2 4x4 8x8 16x16 32x32 64x64のうちから選べます。
      この機能を使うことで１次変換にともなうテクスチャの歪みの問題およびニア
      クリップ(near clip)問題を解消することができます。
      ただし分割数を多くしすぎると速度およびメモリ使用量が増大しますので注意
      が必要です。
      自動分割機能を備えたパケット作成関数はGsSortObject4()及びGsSortObject5()
      です。
      自動分割機能を使う場合はパケット作成関数の最後の引数にワークとして使用
      するスクラッチパッドのアドレスを渡す必要があります。

 4 視点
--------

    ３Dグラフィックスでは画面に映し出される画像は視点の前に設定されたスクリー
    ンへの投影となります。
    そのため画面に画像を映し出すには視点及びスクリーンを設定する必要がありま
    す。

  4.1 視点の設定

    視点の設定はGsRVIEW2もしくはGsVIEW2の構造体に値を代入してGsSetRefView2(),
    GsSetView2()で設定します。
    GsRVIEW2とGsVIEW2の違いは、視点の設定方法にあります。
    GsRVIEW2は視点と参照点の座標を設定することで、視点を設定します。
    GsVIEW2は視点座標系への変換マトリックスを直接設定することで視点を設定しま
    す。
    GsVIEW2,GsRVIEW2ともに構造体のsuperに設定する座標系を書くことができます。
    ワールド座標に設定すれば通常の客観視カメラになりそれぞれの物体のローカル
    座標系に設定すればその物体の主観視カメラになります。

  4.2 スクリーンの設定

    視点の前方にはスクリーンが設定されます。
    視点とスクリーンとの距離をプロジェクション（h）と言い、GsSetProjection()
    で設定します。
    
        図 2 視点とスクリーン

    スクリーンの縦、横は画面の解像度になります。
    例えば６４０x４８０の解像度であれば、スクリーンの横は６４０、縦は４８０に
    なります。
    画面の解像度が、正方ドットでない場合（つまり画面の解像度の横縦の比が４対
    ３でない場合）縦が調整されます。
    例えば６４０x２４０ドットの場合は、物体の縦が１／２に縮小されて表示され見
    かけ上は正方ドットのアスペクト比と同じになります。
    GsInit3D()をコールすると、スクリーンの中央がスクリーン座標の原点となりま
    す。
    libgsの３D部分を使う場合必ずGsInit3D()を一度呼ぶ必要があります。
    プロジェクションは、画角を調整します。
    プロジェクションが大きければ画角が狭まり平行投影に近くなります。
    プロジェクションが小さければ画角が広がりより遠近感の強調された画像になり
    ます。

 5 光源
--------

    PlayStationでは平行光源を３つまで同時にあてることができます。
    平行光源とは、光源とポリゴンの角度のみで明るさが決まる光源のことです。
    光源は光源の向きと色とで設定します。

  5.1 光源の設定

    光源は、GsF_LIGHT構造体のパラメータを設定してGsSetFlatLight()でlibgsに設
    定します。
    平行光源は３つまで設定可能なためGsSetFlatLight()の引数のIDは0～２までを指
    定します。

  5.2 アンビエント

    アンビエントとは周囲光のことです。光があたっていなくても周囲光によりもの
    の形は見ることができます。アンビエントはこのような現象を実現するために用
    意されています。
    アンビエントの設定は以下のように設定します。光のあたっているところを１と
    した時に光のあたっていない部分を0.5とするとアンビエントはGsSetAmbient（
    ONE/2,ONE/2,ONE/2)に設定します。ここでONEとは固定小数点で１のことです。
    パラメータが３つあるのはRGB独立にアンビエントを指定できるからです。
    一般にアンビエントを上げると暖かいイメージになり、下げるとつめたいイメー
    ジになります。

  5.3 デプスキューイング

    視点からの距離（Z）に応じて物体の明るさを変化させると遠くのものを霞ませる
    ことができます。この効果をデプスキューイングと呼びます。
    libgsではテクスチャつきでないすべてのポリゴンに対してデプスキューイングを
    行なうことができます。
    デプスキューイングを行なうには、GsSetLightMode(1)もしくはGsSetLightMode(3)
    をコールしてデプスキューイングの光源計算を指示します。
    そして、GsFOGPARMのrfc,gfc,bfcにバックグラウンドカラーを設定し
    GsSetFogParam()でlibgsに設定します。
    バックグラウンドカラーが白っぽくするとFOG効果となります。
    テクスチャマップされたポリゴンに対してはバックグラウンドカラーが黒の時の
    みこの方法でデプスキューイングが可能です。
    これはダンジョンなど遠くを暗くして見えなくする時などに有効です。
    テクスチャマップされたポリゴンをどんな場合でもデプスキューイングさせるに
    はCLUTを奥行きによって切り替えることで実現できます。この方法は現在libgsで
    はサポートされていません。
    なお、バックグラウンドカラーと周辺光（アンビエントカラー）は一般には異な
    るので注意が必要です。

  5.4 マテリアルライティング

    ポリゴンと光源の角度で光の強さが決定されると説明しましたが、その光の減衰
    カーブをより急峻にすることで物質の質感を金属質に変えることができます。こ
    れをマテリアルライティングと呼びます。
    マテリアルライティングを行なうにはGsSetLightMode(2) or GsSetLightMode(3)
    をコールしてマテリアルライティングを指示します。
    減衰の制御はオブジェクト毎にattributeで行ないます。attributeのマテリアル
    減衰のところで０から３の値を設定します。設定した値が大きい程減衰がきつく
    なり、金属的な質感が増します。ただし、現在のバージョンではまだ対応してお
    りません。

 6 描画の優先順位（オーダリングテーブル）
------------------------------------------

    PlayStationでは、陰面消去をポリゴン描き順（Zソート）によって実現していま
    す。
    そして高速なZソートを実現するためにオーダリングテーブル(OT）という概念を
    導入しています。
    OTとはメモリ上にとられたZの「物差し」の様なもので物差しのそれぞれの「目盛」
    がいくつでもポリゴンを持つことができます。
    ソーティングは、ポリゴンのZ値に応じて、そのZ値と等しい目盛へポリゴンを「
    置いて」いくことで行ないます。ポリゴンを最後まで置いていくと、物差しには
    すべてのポリゴンがZ値に応じてぶら下がっていることになります。
    これを目盛の順に描画装置へ転送し描画していくことで、陰面消去を実現できま
    す。

  6.1 GsOT

    GsOTは、オーダリングテーブルハンドラと呼ばれる構造体です。libgsではOTを
    GsOTでハンドルしす。この構造体にはOTの実体へのポインタとそのOTの属性を示
    すパラメータが格納されています。メンバorgがOTの実体へのポインタです。
    OTにはZの目盛の解像度を２の１乗から１４乗までの１４段階の設定をすることが
    できます。この情報をメンバlengthに保持します。

  6.2 GsOT_TAG

    GsOT_TAGは、OTの実体を構成する最小単位です。GsOT_TAGは先ほどの物差しのた
    とえでいうと物差し一目盛のことです。
    GsOT_TAGの配列としてOTの実体が定義されます。例えばlengthが４であった場合、
    ２の４乗すなわち１６のOT_TAGの配列がOTの実体になるということです。

  6.3 OTの初期化

    OTの初期化はGsClearOt()によって行ないます。GsClearOt()はoffset,point,otp
    の3つの引き数をとります。otpはOTハンドラへのポインタです。offset,pointに
    ついては後述します。
    OTは初期化されるとポリゴンを全くかかえていない状態となり、ソート可能とな
    ります。
    ソートをする前に必ず初期化を行なう必要があります。

  6.4 複数OT

    libgsではOTを複数持つことが許されています。複数のOTはGsSortOt()によってOT
    同士をソートすることができます。この時にOTの代表値Zとして参照される値が構
    造体GsOTのメンバにあるpointです。
    複数のOTを用いることにより、ソートの順番を制御することが可能となります。
    例えば、オブジェクト毎にローカルOTを用意し、最後にローカルOTをソートして
    まとめれば、オブジェクト単位のソートが可能です。
    これは、道路の上を自動車が走っているところをヘリコプターで上から見下ろし
    ている時などの、前後関係が既にわかっている場合などに有効です。

  6.5 OTの圧縮

    OTを用いることで、ソートのスピードは高速化されますが、そのかわりOTはメモ
    リを消費します。OTでメモリをあまり消費しないようにするには、OTのlengthを
    少なくしてOTの解像度を下げる方法があります。ところが、OTの解像度を下げる
    とソートの際の解像度も下がってしまい前後関係の間違いにるポリゴンがちらつ
    く現象（Zソート問題）が起こりやすくなってしまいます。
    解像度を落さずにOTのメモリ使用量を減らす方法としてオフセットを使うという
    方法があります。これは、ソートされるポリゴンのZ値がある値よりも大きいこと
    がわかっている場合に使用できます。その値をoffsetとしてGsClearOt()に渡せば
    OTはoffsetまでの部分をメモリにとりません。これによりメモリ使用量を減らす
    ことができます。

  6.6 Zソート問題

    Zソート問題とは、Zソートにより陰面消去をする際に優先順位を取り違えてポリ
    ゴンがちらつく現象を指します。
    これは優先順位を決定する際に参照されるZがポリゴン１つにつき１つであること
    が原因です。とくに奥に長いポリゴンはZの値が、一つのポリゴンで大きく広がっ
    ているにもかかわらず、ただ一つの代表値Zでしかソーティングされません。
    libgsではポリゴンの重心のZをソーティングの際に参照しています。
    Zソート問題を解消するには、ポリゴンを細かく分けるという方法が１つあります。
    しかしポリゴン数の増大は避けられません。
    もう一つの回避策としてオブジェクト単位のソーティングがあります。オブジェ
    クト毎の前後関係が明らかな場合はこの条件を反映させてソーティングすること
    でオブジェクト同士で干渉することのないソーティングが可能です。

  6.7 OTのダブルバッファ

    ポリゴンを割り付けられたOTはそのOTが描画されている間にはアクセスできませ
    ん。
    そのため、バックグラウンドで描画をする場合は、OTを二つ用意し描画に使われ
    ていないOTをソーティングに使わなくてはいけません。

 7 表示のダブルバッファ
------------------------

    PlayStation２次元のフレームバッファをもち 画面に表示されるイメージは、フ
    レームバッファに書き込まれたものが、そのまま再現されます。
    表示は垂直基線同期（Vブランク）の間に切替えると画面が乱れずに切替ができま
    す。
    切替えられた画面は、その画面がテレビの画面が表示 されている間にアクセスさ
    れると画面が乱れてしまいます。
    そのために表示されている面と、書き換えられている面の二つの面が必要です。
    これを表示のダブルバッファと呼びます。
    libgsではGsDefDispBuffer()によってダブルバッファを定義しています。
    この定義されたダブルバッファは、GsSwapDispBuff()によって切替が起こります。
    現在ダブルバッファのどちらに描画しているのかはGsGetActiveBuff()によって得
    ることができます。

  7.1 ダブルバッファの実現

    ダブルバッファは内部ではフレームバッファの表示位置を変えることで実現して
    います。
    画面上のに表示領域の左上点（原点）は、必ずしもフレームバッファの左上点に
    ある必要はありません。
    この時は、フレームバッファへオフセットつきで描画をする必要があります。
    このオフセットをつける段階をlibgsでは二通りから選ぶことができます。
    ひとつはlibgteレベルでオフセットをつける方法です。
    この方法を選択するとパケットを計算して作る段階でダブルバッファのオフセッ
    トが付けられます。
    もうひとつはlibgpuレベルでオフセットをつける方法です。
    この方法を選択すると、ダブルバッファのオフセットはパケットにはつかず、フ
    レームバッファに描画する段階でオフセットが付けられます。
    このどちらの方法をとるかGsInitGraphの第３引数で選択できますが、libgpu関数
    との併用を予定している場合は後者の方法を選択することをお勧めします。
    現在前者の方法を用いるメリットは以前のバージョンとの互換性を保つ以外はあ
    りません。

  7.2 インターレース時のダブルバッファ

    インターレースの時は縦解像度として４８０の倍解像度を指定することが できま
    す。
    この時のダブルバッファはフィールドの偶数・奇数で自動的に行なわれるため、
    GsDefDispBuff()でのダブルバッファの設定は同じバッファを指定する必要があり
    ます。
    インターレース時に縦解像度を２４０とする場合はノンインターと同じように違
    うバッファを設定する必要があります。

 8 クリッピング
----------------

    libgsではクリッピングは２Dのクリッピングと３Dのクリッピングの二つにわけら
    れます。
    ２Dのクリッピングはスクリーン座標系に変換した後にクリッピングすることです。
    ３Dのクリッピングは視点からの距離に応じてクリッピングするものです。

  8.1 ２Dクリッピング

    PlayStationにはフレームバッファの任意の矩形をクリッピング領域として指定で
    きる機能があります。
    GsSetClip2D()によりlibgsの内部変数にクリッピング領域を登録します。
    GsSetDrawBuffClip()はその変数の内容を設定し有効にします。
    表示のダブルバッファの切替えは、クリッピング領域も切替えてはみ出したポリ
    ゴンが、別のバッファを壊さないようにしています。

  8.2 ３Dクリッピング

    libgsでは、３Dのクリッピングはアプリケーションレベルで行なうことを前提と
    して設計されており、ライブラリレベルでの３Dクリッピングはデフォルト値以外
    は、サポートされていません。
    デフォルトの３Dクリップ値には、以下のものがあります。

   (1) 遠方クリップ

      スクリーン座標系のZ値は符合なし１６ビットなのでZが６５５３６以上の時に
      クリップされます。

   (2) 近方クリップ

      プロジェクションをhとしてスクリーン座標系のZ値がh/2以下の時にクリップさ
      れます。

  8.3 ニアクリップ問題

    「ニアクリップ(near clip)問題」とは、レーシングゲームの路面などポリゴンが
    視点に限りなく接近してかつポリゴン自体が視点に近付いているため巨大になる
    場合に起こるさまざまの問題を言います。
    ポリゴン単位でクリップした場合視点近くの路面に大きな穴があいてしまい、非
    常に見にくくなってしまいます。libgsではこの問題の解決策としてポリゴンの自
    動分割をサポートしてます。
    オブジェクトが接近した場合attributeの自動分割を設定することによりニアクリ
    ップを円滑に行なえます。
    ただし自動分割は負荷が重いので本当に必要な時の使用に限定してください。

 9 パケット作成関数群
----------------------

    libgsはGsSortObject3()GsSortObject4()GsSortObject5()の３つのパケット作成
    関数を状況に応じて選択可能です。

  9.1 パケットバッファ

    パケットバッファには以下の二つの種類があります。
    
      (1) プリセットパケットバッファ
      (2) ランタイムパケットバッファ
    
    (1)のプリセットパケットバッファはプリセットパケットのオブジェクトを使う時
    に必要です。
    プリセットパケットを使うオブジェクトタイプはGsDOBJ5を使うGsSortObject5()
    関数です。
    プリセットパケットのサイズはモデルにより固定です。
    GsPresetObject()の返り値によってどこまでバッファがプリセットされたか知る
    ことができます。
    プリセットは最初に１回必要です。
    プリセットパケットはプリセットバッファの領域にパケットを作るのでランタイ
    ムパケットバッファを消費しません。
    ただしGsDOBJ5のattributeで自動分割をONにした時はランタイムパケットバッフ
    ァにパケットを作るのでランタイムパケットバッファを消費します。
    (2)のランタイムパケットバッファは実行時にパケットを作るためのバッファです。
    これを使うのはGsSortObject4(),GsSortSpriteなどです。
    バッファの先頭はGsSetWorkBase()により指定されGsSortObjet4()が呼ばれる度に
    その領域にパケットを作っていき、カレントのパケット領域のポインタは
    GsGetWorkBase()により取り出せます。
    バッファのサイズは１フレームに同時に表示されるために計算されるポリゴンの
    数により増減します。

  9.2 プリセットパケット

    プリセットパケットとはパケットをあらかじめ作っておくということです。
    そうすれば毎フレーム書き換えなくてもいい項目、例えばテクスチャのu,vなどは、
    メモリにライトしなくてもいいため高速化されます。
    PMDフォーマットはプリセットパケット専用のモデリングフォーマットです。
    GsSortObject5()はプリセットパケットのパケット作成関数です。
    プリセットパケットを作るにはGsPrsetObject()を用います。
    
        図 3 プリセットパケットのフォーマット

    パケットは、libgpu.hのPOLY_FT4などの構造体（プリミティブ）の集まりです。
    プリミティブの種類はタイプを見れば判別できます。
    tpageをセットしたければ、POLY_FT4などの構造体のtpageをセットすることで行
    なうことができます。

  9.3 TMDのソート

    TMDフォーマットのモデリングデータは、さまざまなポリゴンの種類がランダムに
    並べてある状態も許容しています。しかし、実際にリアルタイムでTMDデータから
    パケットを作成するにあたって、ランダムなポリゴンタイプの出現は、その切替
    の度に、デコードルーチンが切り替えられインストラクションキャッシュの威力
    を十分発揮できません。
    そのためにTMDデータ中のポリゴンタイプをまとめておくという高速化の手法があ
    ります。これがTMDソートです。
    TMDをソートはオーサリングレベルで行ないます。変換のためのコマンドは、
    TMDSORT.EXEです。このコマンドの解説はオーサリングツールの方の解説を参考に
    して下さい。
    GsSortObject4(),GsSortObject5()どちらのパケット作成関数もソートされたTMD
    データを使用すれば高速化の効果があります。

  9.4 パケット作成関数


   (1) GsSortObject3()

      GsSortObject3()は、PMDフォーマットのパケット作成を行ないます。
      オブジェクトハンドラはGsDOBJ3を使います。
      PMDデータをGsDOBJ3でハンドルするにはGsLinkObject3()を一度呼んで TMDデー
      タとハンドラとを関連付ける必要があります。
      PMDフォーマットというのはモデリングデータとプリセットパケットが、一体と
      なったフォーマットです。TMDからPMDへのコンバートはオーサリングレベルで
      行ないます。
      変換のためのツールはTMD2PMD.EXEです。詳細はオーサリングツールの解説を参
      考にして下さい。

   (2) GsSortObject4()

      GsSortObject4は最も汎用的なオブジェクト計算ルーチンです。高速化のために
      ソートされたTMDフォーマットのデータを使用します。TMDデータのソートは
      tmdsort.exeコマンドで行ないます。オブジェクトハンドラとしてはGsDOBJ2を
      もちいます。
      TMDデータをGsDOBJ4でハンドルするにはGsLinkObject4()を一度呼んでTMDデー
      タとハンドラとを関連付ける必要があります。
      あらかじめセットされたローカル／スクリーンマトリックスとローカル／スク
      リーンライトマトリックスを参照してオブジェクトをローカルスクリーン変換
      しソーティングしてOTに割り付けます。
      ローカル／スクリーンマトリックスのセットはGsSetLsMatrix()により行ないま
      す。ローカル／スクリーンライトマトリックスのセットはGsSetLightMatrix()
      により行ないます。
      OTに割り付けられたポリゴンはGsDrawOt()によって描画されます。この描画関
      数はすぐリターンし、描画はバックグラウンドで行なわれます。

   (3) GsSortObejct5()

      GsSortObject5はプリセットパケットを用いたパケット作成関数です。高速化の
      ために、ソートされたTMDフォーマットのデータを使用します。TMDデータのソ
      ートはtmdsort.exeコマンドで行ないます。オブジェクトハンドラとしては
      GsDOBJ5を使用します。
      TMDデータをGsDOBJ5でハンドルするにはGsLinkObject5()を一度呼んでTMDデー
      タとハンドラを関連づける必要があります。
      プリセットパケットを作成するにはGsPresetObject()を用います。
      GsSortObject5()でパケットを作成するためにはGsPresetObject()をイニシャラ
      イズで一度呼び、プリセットパケットを作成しておく必要があります。

   (4) 機能比較

      これらの関数の特徴を以下に示します。

 10 パケット領域
-----------------

    GsSortObject4()は、パケットを作成しオーダリングテーブルに割り付けます。
    パケットが作られる領域は、GsSetWorkBase()によってlibgsに設定します。
    パケットはポリゴンの種類（フラット／グーロー、テクスチャあり／なし）や数
    によって増減するためパケット領域をどれくらいとればいいかは大体にしか見積
    もれません。
    ただし、パケット領域が実際に作成されるパケットより小さい場合は、パケット
    領域の後ろにある領域は壊されるので注意が必要です。
    現在、パケット領域がどのくらいまで使われているかを返す関数が
    GsGetWorkBase()です。
    この関数によって、プログラマはオーバフローの危険性を予知できます。
    GsSortObject5()を使った場合はプリセットパケットのエリアにパケット領域が予
    めとられているためGsSetWorkBase()を使用して、新たにパケット領域を確保する
    必要はありません。
    ただし、自動分割の機能を使う場合は、分割して増えた分のパケットは
    GsSetWorkBase()で設定したパケット領域に作られるのでGsSetWorkBase()による
    パケット領域の設定が必要です。

  10.1 パケットのダブルバッファ

    描画をバックグラウンドで行なうため、描画中のパケットは壊すことができませ
    ん。そのためパケット領域を二つとりダブルバッファにする必要があります。

 11 描画について
-----------------

    描画はGsDrawOt()によりスタートします。描画面はGsSwapDispBuff()がコールさ
    れるたびに切り替わります。描画はバックグラウンドで行なわれるため、描画に
    十分時間をかけることができます。
    描画のプロセスはまず、描画面に残っている２フレーム前のイメージを消してか
    らGsSortObject...()で作成されたパケットを描画していくことで行なわれます。
    画面をクリアするためのパケットを、OTに登録する関数がGsSortClear()です。
    引数により、任意の色にクリアできます。

 12 Gsライブラリでのスクラッチパッド使用量
-------------------------------------------

    Gsライブラリでは、GsSortObject4,GsSortObject4J,GsSortObject5,
    GsSortObject5Jでスクラッチパッドのアドレスを引数で渡します。これは、ポリ
    ゴン分割の際に、スクラッチパッドを使用することでスピードを向上させるため
    です。ここでは、Gsライブラリがどんな状況でどの程度スクラッチパッド領域を
    使用するのかを説明します。

  12.1 スクラッチパッドを消費する状況

    スクラッチパッドを使用する状況は、以下の関数および、attributeを使用した場
    合です。

        表 5 スクラッチパッドを消費する状況
    +---------+----------------------------------+
    |関数名    GsSortObject4()                   |
    |          GsSortObject4J()                  |
    |          GsSortObject5()                   |
    |          GsSortObject5J()                  |
    |attribute GsDIV1,GsDIV2,GsDIV3,GsDIV4,GsDIV5|
    +---------+----------------------------------+
    
    自動分割を行わない場合は、スクラッチパッド領域は消費しません。

  12.2 スクラッチパッドの消費量

    スクラッチパッドの消費量は、以下の通りです。(単位byte)

        表 6 スクラッチパッドの使用量
    +-------------------+------+------+------+------+------+
    |                    GsDIV1 GsDIV2 GsDIV3 GsDIV4 GsDIV5|
    |3角形ポリゴンの場合 184    272    360    448    536   |
    |4角形ポリゴンの場合 260    400    540    680    820   |
    +-------------------+------+------+------+------+------+

  12.3 ユーザプログラムとライブラリでスクラッチパッドを共用する方法

    GsSortObject...()の引数で与えるスクラッチパッドのベースアドレスを下位にず
    らし、上位をユーザプログラムで使用します。ライブラリの使用するスクラッチ
    パッド領域は、アドレス的には下に伸びます。

 14 ＨＭＤ用ライブラリ
-----------------------

    HMDとは、Hierarchical Model Dataの略称で、Ver4.0のgsライブラリで新たに導
    入されたフォーマットです。HMDはモデルデータからイメージデータ、アニメーシ
    ョンデータなどの広範なカテゴリのデータをカバーします。また拡張性があるた
    め新たなデータフォーマットを付け加えていくことが可能です。
    
    HMDを利用するためにはVer4.0以降のプレイステーションライブラリが必要です。
    データ作成のツールとしてはRSD2HMD.EXEを利用できます。
    

  14.1 HMDのコンセプト

    従来のlibgsでは多種多様なポリゴンフォーマットに対応するためジャンプテーブ
    ルという機能を導入してきました。HMDはこの考え方を推し進め、データの中にそ
    のデータを処理するためのライブラリ関数の先頭アドレスを埋め込みます。埋め
    込まれるライブラリ関数をプリミティブドライバと呼びます。多種多様なデータ
    を統一的に管理するため３２ビットのtypeと呼ばれる識別子を導入し、どのプリ
    ミティブドライバをどのtypeのデータに埋め込むかを統一的なルールで管理しま
    す。
    
    データの拡張性を向上させるためtypeを加えることで新たなフォーマットを追加
    できるような枠組みにしています。またプリミティブドライバに関しても、ライ
    ブラリとして供給される他ユーザ定義も可能にするため呼び出しのシーケンスを
    標準化しています。これによりユーザはHMDの枠組みの中で独自のフォーマットを
    追加することが可能であるばかりでなく既存のtypeに関しても独自のプリミティ
    ブドライバを書くことが可能となっております。
    

  14.2 HMDで新たにサポートされる機能

         ・モデルデータにテクスチャイメージデータを含ませることが可能になりま
           した。
         ・モデルデータに座標系の情報を持たせることができるようになりました。
           これにより座標系の異なるオブジェクトを一つの論理オブジェクトとして
           定義でき座標系同士の結合情報やオブジェクトの配置情報もＨＭＤの中に
           入れることができるようになりました。
         ・複数の座標系にまたがるポリゴン（共有ポリゴン<SHARED POLYGON>と呼ぶ）
           を定義し表示することが可能になりました。この技術によりONE SKIN 
           MODELと呼ばれる滑らかな関節を持つモデルが表示可能になりました。
         ・モデルデータにそのモデルのアニメーションの情報を定義することができ
           るようになりました。アニメーションのアルゴリズムとしてはキーフレー
           ム補完　および　MIMeが可能です。ただしMIMeに関してはVer4.1で正式サ
           ポートの予定です。
         ・連結ポリゴンがサポートされました。これでモデルをより少ない頂点デー
           タで表現でき計算も高速化されます。自動的に連結情報を検索するツール
           MESHCONV.EXEを提供します。
    

  14.3 ＴＭＤからＨＭＤへの移行

         (1) 計算関数の変更
         2. GsSortObject3,4,5からGsSortUnit()へ変更します。
         3. 
         (4) オブジェクトハンドラの変更 オブジェクトハンドラをGsDOBJ3,4,5から
             GsUNITに変更します。GsDOBJ3,4,5に存在したattributeはGsUNITでは削
             除されました。HMDではプリミティブドライバの振る舞いをattributeで
             制御するのではなくプリミティブドライバを切り替えることにより行い
             ます。  GsUNITには二つのメンバがあります。coordは座標系へのポイ
             ンタを保持します。primtopはプリミティブブロックの先頭を保持しま
             す。 GsSortUnit()を呼び出す前にcoordからローカルワールドマトリッ
             クスを計算しGTEにセットすることは今までと同じです。 primtopは
             GsSortUnit()に渡します。 
         (5) 初期化手順の変更 GsMapUnit()でＨＭＤで基本的に定義されているポイ
             ンタを実アドレスに変換します。 GsScanUnit()でプリミティブドライ
             バへのポインタを埋め込むためのアドレスとtypeを取得します。typeの
             ビットを見てどのプリミティブドライバを結合させるべきか判断し取得

             コーディネートのマップ（GsMapCoordUnit）など）を呼び出します。

 15 ＨＭＤライブラリ（アニメーション用）
-----------------------------------------

    ＨＭＤ用のライブラリはアニメーションの処理もサポートしています。ＨＭＤが
    コーディネート情報を持っているので階層化されたモデルのモーションの記述が
    可能です。
    
    ＨＭＤのアニメーションの特徴は、Realtime Motion Switchによるインターラク
    ティブなアニメーションシーケンスの制御があげられます。この技術はあらかじ
    め定義しておいた複数のモーションのシーケンスパターン間を任意のタイミング
    で移動するものです。これにより見栄えのするモーションを作成するというオー
    サリングレベルのチューニングを可能としながらゲームに不可欠なインターラク
    ティブ性を実現しています。
    
    ＨＭＤアニメーションデータのメモリ使用量はシーケンスを使いまわすことを可
    能にすることで極小に押さえてあります。実体を表すデータは一つしか存在せず
    他はすべてインデックスやポインタで参照されています。
    
    ＨＭＤアニメーションのキーフレーム補完の方法は、ＨＭＤのTypeにより管理さ
    れるため様々な補完方法を提供することが可能です。またTypeを追加することで
    新たな補完方法を定義すること可能です。
    補完を行うPrimitive Driverとして、マトリックスの回転および平行移動をリニ
    ア補完するライブラリが提供されています。ベジェカーブによる補完関数は
    Ver4.1で提供される予定です。
    

  15.1 アニメーションの定義


    シーケンスコントロール記述子

    一つのアニメーションシーケンスは、シーケンスコントロール記述子（SC）の羅
    列により定義します。SCは16bitのデータです。SCには二つの種類があり、一つは
    キーフレーム記述用のＳＣ(SCK)、もう片方はジャンプ記述用のＳＣ(SCJ)です。
    
    SCKはキーフレームの実体を表すメモリエリアへのインデックスが保持されます。
    SCJは飛び先のＳＣＫのインデックスを保持します。SCKはキーフレームの実体へ
    のインデックスの他、次のキーフレームまでの時間的距離（TFRAME）、および補
    完のための関数のインデックス(Type Idx)を保持します。
    
    全てのシーケンスはストリームID(SID)という７ビットのIDを一つ保持します。
    SCJはSRCストリームID(
    SSID)とDSTストリームID(DSID)の二つを保持します。SCJによりジャンプが行われ
    るのはSSIDがそのシーケンスの持つSIDと一致した場合に限られます。一致しなか
    った場合はそのまま直後のSCへポインタが移ります。DSIDはジャンプが起こった
    場合飛び先でのSIDを決定します。ただしSID＝０の場合は特別なIDです。このID
    はすべてのSIDと無条件にマッチします。
    

    シーケンスヘッダ

      シーケンスヘッダは個々のシーケンス情報を一元管理します。シーケンスヘッ
      ダは
        1．シーケンスポインタ
        2．シーケンス情報
      の2つの部分から構成されます。
      
      シーケンスポインタはアニメーションの再生のコントロールを指示します。こ
      れについては後述します。
      
      シーケンス情報は個々のシーケンスの情報を保持しシーケンスの数だけリスト
      されます。一つのシーケンス情報は、シーケンスの先頭インデックス、ストリ
      ームIDの二つの情報を保持します。シーケンスの先頭インデックスはSCの羅列
      される領域のそのシーケンスが開始されるインデックスを保持します。ストリ
      ームIDはそのシーケンスを再生する時点でのSIDを指示します。
      これらの情報は全てユーザプログラムにより参照されユーザプログラムにより
      シーケンスポインタを通してライブラリに通知することでシーケンスをコント
      ロールします。
      
      

  15.2 アニメーションの再生


    フレームアップデートドライバ

      フレームアップデートドライバとはシーケンスを時系列で解釈し、補完のため
      の適切な補完関数を呼び出す働きをするドライバです。
      
      フレームアップデートドライバはHMDのプリミティブドライバと同じ枠組みで組
      み込まれます。Ver4.0のLibgsで提供されているフレームアップデートドライバ
      GsU_03000000()は、Realtime Motion Switch, 正逆再生、1/16までのスロー再
      生、8倍までの高速再生が可能です。
      

    補完ドライバ

      キーフレームの補完を行うための関数です。フレームアップデートドライバと
      同じようにTypeにより識別されますがＨＭＤの標準のプリミティブドライバの
      枠組みではインプリメントされていません。 よってSCANに関しては標準のSCAN
      関数GsScanUnit()ではなく専用のSCAN関数GsScanAnim()を用います。
      SCANが終わると補完ドライバへのポインタは専用の領域（補完関数テーブルセ
      クション）に羅列されることになります。
      SCKはType Idxによりどの補完ドライバを呼び出せばよいかをキーフレーム毎に
      インデックス指定します。これにより一つのシーケンス内でキーフレームの補
      完方法を切り替えることができます。
      

    シーケンスポインタ

      シーケンスポインタはアニメーションの再生ポイントの情報を保持します。こ
      のポインタを通じてアニメーションの再生をコントロールすることが可能です。
      
      シーケンスポインタには以下の要素が保持されます。
         (1) Rewrite IDX	アニメーションによりどこを更新していくのかを指示しま
             す。
         (2) NUM	そのシーケンスポインタに代入可能なシーケンスの個数を保持しま
             す。
         (3) INTR IDX	現在のパラメータを保持するための領域を指示するSCKのイン
             デックス
         (4) AFRAME	シーケンスの絶対フレーム番号を管理します。
         (5) SRC INTRIDX INTR IDXに指定するべきパラメータ保持領域を保持します。
         (6) SPEED	再生スピード
         (7) TFRAME	キーフレーム間の時間的距離
         (8) RFRAME	キーフレームからの時間的距離（デクリメントされる）
         (9) Stream ID	シーケンスのID番号
         (10) TCTR IDX	ターゲットのキーフレームを保持するSCへのインデックス
         (11) CTR IDX	元のキーフレームを保持するＳＣへのインデックス
         (12) START IDX	シーケンスの開始インデックスを保持します。
         (13) START SID	シーケンスの開始時のSIDを保持します。
         (14) TRAVELING	キーフレームの変わり目で０にリセットされる変数です。自
              由に使用可能です。
         15. 
      これらのパラメータはプログラマによってのみセットされるものとフレームア
      ップデートドライバによって更新されるものがあります。詳細はGsSEQ構造体の
      リファレンスを参照してください。
      

  15.3 Realtime Motion Switch

    この機能はインターラクティブアニメーション実現するための機能です。ＨＭＤ
    のフレームアップデートドライバおよび補完ドライバにインプリメントされてい
    ます。Realtime Motion SwitchはSIDによるキーフレーム単位でのシーケンスの切
    り替えと補完途中からの即時切り替えの二つの機能に分けられます。
    

    SIDを用いたシーケンスの切り替え

      通常のシーケンス
        ジャンプのないシーケンス
      
      
        ジャンプのあるシーケンス
      
      これはSCK1-2の後にSCJ1記述子を書いておくことで、もしSidが１であった場合
      SCK2-1へ分岐します。SCJ1の記述子にはジャンプ後のSidを0にするという情報
      を書いておけばジャンプ後はSidは０にセットされます。もちろんSCJ記述子は
      複数直列に並べることも可能ですのでいろいろなSidに対して個別のジャンプ先
      を指定することも可能になります。
      
      SCJ1の記述子をシーケンスポインタが通る前にSidを０から１へ書き換えること
      で実行時にシーケンスの分岐を制御することが可能です。
      
      ループのシーケンス
    
      ループのシーケンスはジャンプ記述子で前方にジャンプすることで実現します。
      SIDが２の間このループは回り続けSIDを１にすることでループをぬけます。SID
      を実行時に書き換えることでループの制御をインターラクティブに行うことが
      できます。

    シーケンスの即時切替

      SIDによるシーケンスの切り替えはキーフレームの切り替わりの時のみシーケン
      スの切り替えが行われます。これはSIDの変更を前倒しで発行できる点、および
      意図したところでのみシーケンスが切り替わるため完全に制御可能であるとい
      う長所があります。反面、キーフレームまで到達しないと反応が現れないので
      反応性の面で問題になる場合があります。これを解消するためシーケンスの即
      時切り替えの機能があります。下図に即時切替のシーケンス図を示します。
      
      キーフレームSCK1-1とキーフレームSCK1-2との間を補完中にいつでもキーフレ
      ームSCK2-1にシーケンスを変更することが可能です。この場合、分岐の点に新
      たに仮想的なキーフレームSCK2-0を定義します。
      
      
      この機能を実現するためシーケンスポインタをどのように設定するかを述べま
      す。あらかじめ現状のパラメータを保持するためのエリアをDUMMYのキーフレー
      ムをいれることで作っておきます。これをSCK2-0と定義します。そしてシーケ
      ンスをスイッチしたそのフレームでINTR IDXにSCK2-0を入れます。次のフレー
      ムでINTR IDXに0xffffをいれます。0xffffはパラメータのアップデートを禁止
      します。これでSCK2-0が指すキーフレームの実体に現在地のパラメータが入り
      ます。
      
      SCK2-0を捕獲できた段階でTCTR IDXにSCK2-1のインデックスをCTR IDXにSCK2-0
      のインデックスを入れます。またTFRAMEとRFRAMEにはSCK2-0からSCK2-1の時間
      的距離を入れます。SIDには次のSIDを入れます。
      
      これにより即時のシーケンスの切り替えを実現しています。
